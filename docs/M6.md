# M6: polish and release

Goal: a stranger can download a release zip, check it, install it, and play an evening with three friends without
thinking about the mod (SPEC, *Definition of done*). M6 adds no gameplay. It locks the mod to the game build it was
made for, ships a zip without the dev tooling, documents what to do when the game updates and when something goes
wrong, and fixes what a review of the settled code turned up. It finishes with the two checks only humans can do: a
4-player 2-hour soak, and the display matrix.

Starts from `main` (M0–M3) and takes in M4 (`m4`) and M5 (`m5`) as they merge. Branch `m6`; the lead merges.

## How the build pin works

- The game's version string is the `text` of `res://VersionLabel.tscn` (`"1.90.12"`). `VersionLabel.gd` copies it into
  `CurrentGame.version`, but only once a label enters the tree. Mods run inside the `ModLoader` autoload's `_init`,
  before `CurrentGame` even exists, so `Compat.gameBuild()` reads the stored property from the scene's `SceneState`
  without instancing anything. Demo builds (`OS.has_feature("demo_build")`) are refused too.
- On a mismatch: one `COOP: REFUSED, ...` log line, no script extensions, no CoopNet, and a notice on the title screen
  that goes away when the player leaves it. The game runs as stock.
- Dev flags, blanked in release zips: `--coop-dev-compat-test` fakes a wrong build to walk the refusal path on the
  real game; `--coop-any-build` runs anyway (for re-running the gates on a new build before bumping, see UPDATING.md).

## How the release zip works

- `python tools/build.py --release` writes `build/dv-coop-release.zip`. Plain `python tools/build.py` still writes
  `build/dv-coop.zip` with everything in it. Whichever one is installed goes into `<game>/mods/` as `dv-coop.zip`, and
  any other `dv-coop*.zip` there gets deleted first, because the game loads every zip in `mods/`.
- Left out: `dv-coop/net/DevBot.gd` (`DEV_ONLY` in build.py). CoopNet's module loop on `m4` already skips missing
  files (`ResourceLoader.exists`), so a release CoopNet loads Cell, RockSync, Own and Npc and silently skips DevBot.
- Blanked: every line from `# coop:dev{` to `# coop:dev}` becomes an empty line. Line numbers stay the same, so
  an error in a player's log points at the same source line. If a block leaves an empty `if`/`func`/`for` behind,
  or a marker is unbalanced, the release build stops.
- Listed: any `--coop-dev-*`, `--coop-autodive`, `--coop-dive-offset`, `--coop-slot=`, `--coop-warp-to-peer`,
  `--coop-any-build` or `DVCOOP_` string still in code outside a block shows up as a warning. `--strict` fails
  the build on any of them, and the M6 gate uses `--strict`.
- Today on `m4`: DevBot left out, 23 dev paths outside blocks (Npc 11, RockSync 5, CoopNet 3, Cell 2,
  FriendOverlay 2). Each owner wraps theirs; where to put the markers is in R27.
- ENet (`--coop-enet-*`) stays in release. It is the LAN option in the README, and verify.py declares it.
- Reproducible: same sources, same bytes. Checked by building twice (same SHA-256), and by a dry run over `m4`'s
  `src/`.

## Gate

Dev automation (lead, on `m6` after M4 and M5 merge):

1. `python tools/verify.py` passes, and reports both zips.
2. `python tools/build.py --release --strict --no-install` passes. Run twice, it gives the same SHA-256. The zip
   holds no `DevBot.gd` and no `--coop-dev` string.
3. Build pin, one game run each, zero `SCRIPT ERROR`:
   a. a normal launch on 1.90.12 logs no `REFUSED`, and `--coop-selftest` still passes;
   b. `--coop-dev-compat-test` with the dev zip logs `COOP: REFUSED`, shows the notice on the title screen, logs no
      `installed extension` line, attaches no CoopNet, and a solo dive plays as stock.
4. The release zip runs the M3 gate 1/4/5 subset on dev3, which needs the dev flags. So run it with the dev zip,
   then confirm the release zip loads, the selftest passes, and an ENet LAN pair forms a cell when flown by hand
   or warped with the dev zip on the other side.
5. Every review finding below is fixed, or deferred in writing by its owner with a reason.
6. An agent that hasn't seen this work follows `docs/UPDATING.md` against the current build (a no-op diff) and
   reaches "pin bumped, gates green" without asking anyone.

**Human gates** (cannot be automated; everything above must be green first):

- **H1: 4-player soak, 2 hours.** Four people on four machines and Steam accounts, at least two networks, release
  zip. Play normally: mine together, split up, re-form cells, one player quits and rejoins, someone dies and gets
  rescued. Pass: zero mod script errors in all four `engine_log.txt`, no desync noticed by any player, authority
  at 60 fps and under 250 kB/s upload (from the logs). Covers the DoD engineering lines "two hours of four-player
  play" and "four-player cell at 60 fps". Needs Tim plus three friends, about 2.5 hours with setup.
- **H2: display matrix.** On real hardware, the friend markers and the build-pin notice are readable and placed
  right, and synced rocks line up: a HiDPI laptop; Windows display scaling at 125 %, 150 % and 200 %; a 4K monitor;
  two monitors, with the game on the secondary, then dragged between monitors with different scaling, in windowed
  and fullscreen. Needs Tim, about 30–45 minutes; two machines only for the sync part.

### Routed to tim-06 (M5)

The lead sent these on 2026-10-25. Fixed on `m5` the same day; not yet run in game.

- **R1  (fixed on `m5`, 4c133a8/84200e3, not yet run in game)** `net/CoopNet.gd:313`**. The Steam receive path reads `p.steam_id_remote`. This game's GodotSteam returns
  `{"data", "remote_steam_id"}` from `readP2PPacket`: the exe contains `remote_steam_id` right after the
  `Steam::readP2PPacket` and `data` strings, and `steam_id_remote` appears nowhere in it. Every Steam packet would
  raise a script error, so Steam transport can't work. All testing so far used ENet, which never reaches this line.
  Fix: `p.get("remote_steam_id", p.get("steam_id_remote", 0))`.
- **R2  (fixed on `m5`, 4c133a8/84200e3, not yet run in game)** `net/CoopNet.gd:187-189`**. `_onP2PSessionRequest` accepts a P2P session from anyone. Fix: accept only
  members of `lobbyId` (`Steam.getLobbyMemberByIndex` loop), and log and ignore the rest.
- **R3  (fixed on `m5`, 4c133a8/84200e3, not yet run in game)** `net/CoopNet.gd:331-349`**. The sender id is the self-declared `env.f`. On Steam the link id
  (`remote_steam_id`) is the truth; on the ENet relay the server forwards without checking `env.f == link`. Any
  peer can speak as another, for example forge `c.leave`/`c.state` for someone else's cell. Fix: on Steam, ignore
  `f` and use the link; on the ENet server, drop envelopes whose `f` differs from the link before relaying or
  handling. On ENet clients, trust only envelopes coming from the server link (1).
- **R4  (fixed on `m5`, 4c133a8/84200e3, not yet run in game)** `net/Cell.gd:305`, `:63`, `:514`**. The cid is `"<id>:<cellSeq>"` and `cellSeq` restarts at 1 when
  the game restarts. `resigned` is never cleared. With Steam ids, which survive restarts: a player resigns cell
  `X:1`, restarts the game, forms a cell again, gets cid `X:1` again, and every peer that saw the resignation
  ignores its `c.state`/`c.ad`/`c.hb` for good. The cell never forms for them. Fix: put `born` (system ms) in the
  cid, and clear `resigned[id]`/`adverts[id]` on `hello`/`bye`/peer gone. RockSync net ids (`RockSync.gd:184`,
  `"<id>:<counter>"`) have the same restart reuse. It's harmless now, because members drop tracked rocks on
  leave, but a session nonce in the id would close it for M4 ownership.

### CoopNet (tim-06)

- **R6  (fixed on `m5`, 4c133a8/84200e3, not yet run in game)** `net/CoopNet.gd:541-568`**. When `spawnByBlueprint` fails (no free spot, or the spot is inside the despawn
  radius, `AsteroidSpawner.gd:291` in the game), the puppet is created and freed again on every physics tick (60
  `createShipByConfig` calls/s) with a log line each time. Fix: a `spawnFailedAt` backoff of 1 s per peer, like
  `cfgAskedAt`.
- **R7  (fixed on `m5`, 4c133a8/84200e3, not yet run in game)** `net/CoopNet.gd:322-327`, `:367-371`**. One ping seq goes to every peer, the first pong erases it, so
  `rtt_ms` measures only the fastest peer. Pings are unreliable, so a lost pong leaves its entry in `pingSent`
  forever (one per second per loss). Fix: `rtt` per peer in `peers[id]`, and drop `pingSent` entries older than 5 s.
  M4's clock-offset estimate needs the per-peer value anyway.
- **R8  (fixed on `m5`, 4c133a8/84200e3, not yet run in game)** `net/CoopNet.gd:194-196`, `:108-110`**. `join_requested` only gets connected when the game was launched
  with `--coop-host`/`--coop-join`; otherwise CoopNet stays idle and an overlay invite does nothing, though the
  README says it works. When it does fire, the old lobby is never left and its peers stay in `peers`. M5's joining
  flows own this. Fix: always connect the Steam signals when the singleton exists, and `leaveLobby` +
  `_peerGone` everyone before `joinLobby`.
- **R9  (fixed on `m5`, 4c133a8/84200e3, not yet run in game)** `net/CoopNet.gd:112-119`**. `_exit_tree` never calls `Steam.leaveLobby(lobbyId)`. Steam cleans up when the
  process exits, but the lobby lingers for others until then.
- **R10  (fixed on `m5`, 4c133a8/84200e3, not yet run in game)** `net/CoopNet.gd:157`, `:261`**. The lobby gets a `build` field that no joiner checks, and `hello` carries no
  mod version, build or protocol number, so a 1.90.12 player and a 1.91 player (or two mod versions) mix and
  desync silently. Fix: `hello` carries `Compat.BUILD`, `MOD_VERSION` and a `PROTO` int. On a mismatch, log
  it, show `name: different mod version (x) or game build (y)` in the overlay's list, and drop the peer. A joiner
  can read the lobby's `build` field before joining.
- **R11  (fixed on `m5`, 4c133a8/84200e3, not yet run in game)** `net/CoopNet.gd:249`**. The ENet display name uses `USERNAME`, which is empty on Linux, giving names
  like `-123`. Fix: fall back to `USER`. verify.py then lists `OS.get_environment("USER")` as declared, which is fine.
- **R24  (fixed on `m5`, 4c133a8/84200e3, not yet run in game)** `net/CoopNet.gd:337-347`**. The ENet relay forwards to `env.to` without checking that the peer is still
  connected. A packet for someone who just left spams "invalid target peer" in `engine_log.txt`, which counts
  against "zero errors". Fix: `if not peers.has(to): return`.
- **R26  (fixed on `m5`, 4c133a8/84200e3, not yet run in game)** `net/CoopNet.gd:351-398`, `net/Cell.gd:569-610`**. Packet fields are read without type checks
  (`msg.seq`, `msg.ids`, `msg.p`, `msg.members`, `msg.off`). A malformed or older-version packet raises a script
  error instead of being dropped. RockSync already validates its packets (`_validRecipe`, the `r.u` checks), so do the
  same here, or let R10's protocol check carry most of it.
